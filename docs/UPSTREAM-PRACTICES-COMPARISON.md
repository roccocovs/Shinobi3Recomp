# Upstream project and release-practice comparison

Read-only comparison reviewed 2026-10-22. This records observable repository practices; it is not a legal opinion or a statement that another project's publication is authorized for this project.

## What the public repositories show

- The Sonic recompilation identifies Genesis Recompiler and Matthew Stan, states PolyForm Noncommercial 1.0.0, and points to separate third-party notices. The framework repository also keeps its own PolyForm terms and a dependency-by-dependency third-party license inventory. These are clear license-boundary and attribution practices.
- Sonic's README says “No prebuilt binaries are distributed,” but the GitHub Releases page contains binary releases: v0.6.0 describes a Windows x64 ZIP with `SonicTheHedgehogRecomp.exe` and launcher assets, the v0.7.1 entry describes Windows x64 packages, and the releases list includes an experimental Linux AppImage. This is a discrepancy between the README's documented policy and the actual releases. The release notes say the ROM is not included; the v0.7.1 notes also say saves, settings, and private captures are excluded. This observation does not establish that any release is legally cleared or that those executables are equivalent to a locally generated executable here.
- Sonic's README says generated C is not checked in and is regenerated by CMake from the user's ROM when ROM/config/discovery inputs change. It documents build prerequisites and commands, controller keys, the supported ROM, and known limits. The game repository consumes the shared engine through a pinned submodule and has per-game tools and integration code. The framework README describes each game as owning its input identity and integration.
- The public Genesis Recompiler tree contains a Sonic `game.toml` with ROM identity, RAM layout, named `functions.extra` addresses, and numerous address-based site entries, plus separate disassembly seed/jump-table/subroutine metadata files. Some site entries describe instruction-level transformations by address and operation kind. This is a clear example of publicly committed ROM-specific configuration and callback/function metadata. Sonic's README says the generated C is not checked in and is regenerated by CMake from the ROM and config/discovery data. That is structurally comparable to this candidate's `project/game/game.toml`, `project/game/shinobi3_spec.c`, and ROM-to-native build pipeline. It is a comparison of function, not a conclusion about the legal status of either game's metadata.
- The Genesis Recompiler's release guide uses a package allowlist and explicit checks for ROMs, dumps, saves, logs, maps, diagnostics, license, and notices. It also asks maintainers to state the source revision and verified scope in release notes. The same allowlist approach is used for this project's separate Windows distribution folder.

## Practical recommendations

Already followed: preserve upstream license files; list third-party licenses separately; describe the user-supplied-ROM requirement; exclude generated C and the ROM from the source repository; document exact ROM identification, reproducible build steps, test coverage, and unverified behavior. The precompiled executable is staged separately as a Release asset.

Adopted: the README links directly to the upstream Genesis Recompiler and to this comparison. This document distinguishes Sonic's README statement from actual release entries and says those releases provide no rights precedent for Shinobi III.

For publication, retain the author-selected license scope and the existing provenance record for `game.toml` metadata. This project has selected Option A: a source repository plus a separate user-ROM-dependent Windows binary release. The executable contains translated game instructions; the staged package inventory and verification status are documented separately. This choice does not rely on Sonic's publication as legal authorization. No change to repository architecture or gameplay code was needed.
